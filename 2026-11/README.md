# AI レポートのモデル比較（2026-11）

[gfdash](https://github.com/air-terminal/gfdash) の AI レポートを、同じ入力（公開デモの合成データ）でモデルだけを変えて作り、
品質・処理速度・改良の余地を調べた記録です。データは合成なので、来場者数などの数値は実在の施設のものではありません。

- 実施: 2026-11-21〜22
- 1件ずつの記録: [`data/runs/`](data/runs/)（条件・本文・段ごとの出力）、一覧は [`data/runs.csv`](data/runs.csv)
- 月ごとにモデルを並べた本文: [`data/side_by_side/`](data/side_by_side/)、プロンプトの全文: [`data/prompts/`](data/prompts/)
- 目視の記録（誤りの一覧）: [`results/reading_notes.md`](results/reading_notes.md)
- 自動の検査・集計: [`results/`](results/)、スクリプト: [`scripts/`](scripts/)（`data/` だけで動きます）

## 0. 対象の AI レポート

gfdash はゴルフ練習場向けのダッシュボード（Django + PostgreSQL）です。来場者数・天候・運営者の所見（「キャンペーンを行った」などのメモ）から、
ローカルの LLM が月次のレポートを書きます。今回比べたのは次の2種類です。

| 種類 | 中身 | 作り方 |
|---|---|---|
| 見通し（forecast_1m） | 翌月の来場者数の予測（Prophet）を、前年や直近3か月と比べて読む | 1回の生成。思考なし |
| 営業レビュー（review） | 終わった月の来場を、予測・前年・天候・所見と比べて振り返る | **多段（staged）**: 段1 来場の推移 → 段2 天候 → 段3 所見の整理 → 段4 まとめ。段1〜3は思考なし、まとめの段だけ思考あり。数値表と見出しの下の表はコードが作る |
|  |  | **1回（single）**: 月の合計だけを渡して1回で書く軽量版 |

多段にしているのは、月の合計だけを渡すと、月の中で何が起きたかを想像で埋めるためです。各段には「提供されていない数値を作らない」
「天候を来場の増減の理由に断定しない」「業務改善の提案をしない」などの指示があります（プロンプトの全文は [`data/prompts/`](data/prompts/)）。

## 1. 要約

- **数値の書き写しは、どのモデルもほぼ正確。** 営業レビュー（staged）は、本文の数値がすべて入力か段の出力にあった
  （llm-jp だけ、旬の合計と1日平均を並べるなどの混同がある）。崩れた表、思考のタグの残り、他言語の混入は 0 件
- **誤りの中心は「数値の意味」。** 当月の値と前年の値の取り違え、多い／少ないの判定の誤り、予測比と前年比の取り違え。
  数値そのものは正しいので、数値の照合では見つからない
- **プロンプトと前後の処理で防げる誤りが多い。** 特に次の4つは、モデルを替えても起き、入力の書き方が誘っている:
  1. 見通しで、予測値に反映済みの予測所見（+10% / +8%）を、もう一度掛ける（2モデル）
  2. 見通しだけ提案を条件付きで許しているため、許さない月にも提案が出る（3モデル）
  3. 所見の整理の段が、日付の無い出来事に日付を作る（llama.cpp の4モデルすべて、8件中8件）
  4. 前年にだけ差が付いた天候の群（猛暑日 +8% など）を、当月の値として書く（2モデル・6件）
- **モデルごとの傾向**（営業レビュー）:
  - gemma-4-31b … 最も速く（中央値 121秒）、土日祝の日数の読みも正しいことが多い。天候を理由に断定しがち
  - gemma-4-12b … 当月と前年の取り違え・比較の向きの誤りが多い
  - qwen3.8-27b … 因果を断定しない・引用数の上限を守るなど指示に忠実。ただし数値が少なく抽象的で、天候の向きを全部逆にした回がある
  - llm-jp-4.1-33b … 誤りが最も多い。数値を多く並べ（上限3を超える）、取り違え・向きの誤り・因果の断定が6件中5件ずつ。
    「仕事帰りの利用が主因」「売上面では前年を下回った」のような入力に無いことも書く。
    ただしこのモデルだけ、思考を止められず、コンテキスト長と KV キャッシュの設定もほかと違う（§2.3）
  - qwen3.8-flash-next（Strata、IQ3_S）… 指示に最も忠実（所見に日付を作らなかったのはこのモデルだけ）。数値が少なく、
    「差の数値が付いていない」のような入力の書き方への言及が多い。見出しの「…」の写しが 9件中1件で再現した
- **追加の測定（§8）:** qwen3.8-flash-next を thinking OFF で回すと、営業レビューが 347秒 → 23秒（IQ3_S）/ 30秒（Q4_K_XL）になった（中央値）。
  所要時間のほとんどは、まとめの段の思考だった。thinking OFF では数値を具体的に引いて読みやすくなる一方、推測や因果の言い切りが増え、
  数値表の書き換え・見出しの欠けも1件ずつ出た（thinking ON では0件）

### 2.3 モデルと推論サーバ

| モデル | 推論サーバ | 量子化 | コンテキスト | KV キャッシュ | GPU の分割 |
|---|---|---|---|---|---|
| gemma-4-12b-it-qat | llama.cpp（ルーターモード、b12464） | QAT Q4_0 | 65,536 | q8_0 | layer |
| gemma-4-31b-it-qat | 同上 | QAT Q4_0 | 65,536 | q8_0 | tensor 1.5:1 |
| qwen3.8-27b（unsloth UD-Q4_K_M） | 同上 | UD-Q4_K_M、MTP の投機的デコードあり | 65,536 | q8_0 | tensor 2:1 |
| llm-jp-4.1-33b-thinking | 同上 | Q4_K_M | **32,768** | **f16** | tensor 1:1 |
| qwen3.8-flash-next（IQ3_S） | Strata（制御 0.1.63） | IQ3_S | 65,536 | （Strata の既定） | （Strata の既定） |

- llama.cpp は同時処理 1（`N_PARALLEL=1`）、Flash Attention あり、`--jinja`
- **llm-jp だけ条件が違う。** KV キャッシュ q8_0 + tensor 分割では生成が 0.86 トークン/秒まで落ちた（入力の処理は正常）。
  f16 + 65,536 は読み込みで GPU のメモリが足りない。f16 + 32,768 にして 約32 トークン/秒に戻った。営業レビューに要るのは 16k なので足りる
- 思考: 営業レビューは `--think`（多段では段1〜3は思考なし、まとめの段だけ思考あり）。見通しは思考なし。
  **llm-jp は思考を止められない**（思考専用のモデル。OFF を送っても思考する）

### 2.4 サンプリング

gfdash はレポートの生成でサンプリングを送らない。推論サーバ側の設定がそのまま効く。各モデルのモデルカードの推奨値に合わせた。

|---|---|---|---|---|---|---|
| gemma-4 12b / 31b | 1.0 | 0.95 | 64 | 0 | 0 | カードの値（カードは min_p に触れていないので使わない） |
| qwen3.8-27b | 1.0 | 0.95 | 20 | 0 | 0 | カードの思考ありの値。llama.cpp はモデルごとに1組しか持てないので、思考なしの段もこの値 |
| llm-jp-4.1-33b | 0.8 | 0.95 | 40 | 0.05 | 0 | カードに推奨値が無いので llama.cpp の既定 |
| qwen3.8-flash-next | 思考あり 1.0 / なし 0.7 | 0.95 / 0.8 | 20 | 0 | 0 / 1.5 | Strata の既定（カードの値を思考の有無で切り替える） |

llama.cpp の実際の値は `/props` で確かめた。seed は固定していない（生成ごとに出力が変わる）。

- **天候を理由に断定**: 「雨や風の発生頻度が高かったことが来場者の減少に寄与」（gemma-4-12b）、「強風が来場抑制に寄与した」（llm-jp）。

### 4.4 見通しの誤り

### 4.5 2周目（同じ条件でもう一度）

同じモデル・同じ入力でも、誤りの場所は回ごとに変わった（例: gemma-4-12b の 2026-04 は、1周目は所見の誤読、2周目は土日祝の日数の誤り）。
「このモデルはこの誤りをする」より「このモデルはこの型の誤りをしやすい」と読むのが妥当。
見出しの「…」の写しも、Strata の 9件中1件（2周目の 04）だけだった。

## 6. 限界

- 1条件あたり1〜2回の生成で、seed も固定していない。モデルの差と生成ごとのばらつきは、2周目の3か月を除いて分けられない
- 目視は営業レビュー staged の 3か月（30件）が中心。05・07・09 は自動の検査だけ
- サンプリングはモデルごとにカードの推奨値で、揃えていない。qwen3.8 は llama.cpp（思考なしの段も思考ありの値）と Strata（モードで切り替え）で扱いが違う
- llm-jp はコンテキスト長と KV キャッシュがほかと違う（2.3）
- 推論サーバ・量子化・GPU の分割が揃っていないので、速度は「この構成でこの速さ」の比較
- 合成データ 1施設分。実データの月の動きは、もっと荒い可能性がある

### 7.1 見通しで、予測値に反映済みの所見の見立てをもう一度掛けることがある

> **概要**
> 見通し（forecast_1m）のプロンプトは、予測所見のイベントを「来場者数への影響の見立て: +8%」の形で渡し、
> 「数値の背景として分析に反映してください」と指示している。一方、予測値（Prophet）はこのイベントを補正としてすでに反映している。
> プロンプトがそれを伝えていないため、モデルによっては予測値にもう一度掛ける。
>
> **再現**（デモの合成データ、Ver2.11.0、forecast/v0.2.0）
> - 2026-07（夏休みキャンペーン +10%）: llm-jp-4.1-33b と qwen3.8-flash-next が「7,102人 × 1.10 ≒ 7,812人」と書いた。キャンペーンは 7/18〜だが月全体に掛けている
> - 2026-10（20周年キャンペーン +8%）: llm-jp-4.1-33b が「7,885 × 1.08 ≈ 8,536人」と書いた
> - 逆に gemma-4-12b は 2026-07 で「7,102人は…+10%を考慮する前のベースラインです」と書いた
> - qwen3.8-flash-next（Q4_K_XL、thinking OFF）は 2026-07 で「メイン予測値 7,102人は、このキャンペーン効果を完全に織り込んだ数値かどうかが明記されていません」と書いた（モデル自身が曖昧さを指摘している）
>
> **案**
> - `com_build_remark_section` の見通し用の行で、予測に使ったイベント（`use_for_forecast` で係数あり）には「（予測値に反映済み）」を添える
> - 見通しのプロンプトに「所見の見立て（%）を予測値に掛け直さないでください。予測値はこの見立てを反映した値です」を足す
> - プロンプトの版を上げる（forecast/v0.3.0）
>
> **確かめ方**: 07・10 を複数のモデルで作り直し、掛け直しが無いことと、反映済みと読めることを見る

### 7.2 見通しのプロンプトだけ、提案を条件付きで許している

> **概要**
> 営業レビューは共通の前置き（`COMMON_RULES`）で、業務改善の提案を一切禁じている。`report_common.py` のコメントは、
> 以前の「悪化しているときだけ簡潔に」という条件付きの許可が「想像の入口になっていた」としている。
> 見通し（`report_forecast`）は共通の前置きを使わず、今も「予測値が前年実績を下回るなど…の場合のみ簡潔に」提案を許している。
>
> **再現**（デモの合成データ、Ver2.11.0）: 予測が前年を上回る月（条件では提案しない月）にも提案が出た。
> - 2026-10: qwen3.8-27b が「提案は不要と判断します」と書いた直後に「人員配置や準備を事前に行っておくことを推奨します」
> - 2026-10: qwen3.8-flash-next が見出し「結論と簡潔な提案」を自分で足し、「告知の前倒し実施など…検討してください」
> - 2026-09: llm-jp-4.1-33b が「扇風機設置、ドリンク販売強化を検討すべき」（入力に無い「予約キャンセル」も持ち込んだ）
>
> **案**
> - 見通しも `com_build_common_header` を使い、提案の禁止を営業レビューと揃える
> - 「この3つ以外の見出しを作らないでください」を足す（提案の置き場として見出しを足していた）
> - プロンプトの版を上げる

### 7.3 営業レビューの所見の整理（段3）が、日付の無い出来事に日付を付ける

> **概要**
> 段3の指示は「出来事の名前、日付（期間）、来場者数への影響の向きを必ず残してください」。所見に時期の書かれていない出来事
> （例:「料金改定と競合施設の開業の影響が残り」）にも、モデルは所見の見出し「[2026年04月の所見]」の年月を付ける。
> まとめの段で「料金改定と競合施設の開業は当月に実施され」のような、所見に無い事実になる。
>
> **再現**（2026-04、staged/v1.1.0）: llama.cpp で動かした4モデル（gemma-4-12b / 31b、qwen3.8-27b、llm-jp-4.1-33b）の段3の出力8件すべて（2回ずつ）が、
> 料金改定・競合開業に「2026年04月」を付けた。qwen3.8-flash-next は IQ3_S では2件とも付けなかったが、同じモデルの Q4_K_XL では付けた。
>
> **案**
> - 段3の指示を「日付（期間）は所見に書かれていれば残してください。書かれていなければ『時期の記載なし』と書き、所見の見出しの年月を出来事の日付にしないでください」にする
> - プロンプトの版を上げる（staged/v1.2.0）

### 7.4 営業レビューの入力で、比較の向きをコードが先に付ける

> **概要**
> 営業レビューの誤りの多くは、数値の書き写しではなく比較の判定（多い／少ない、当月か前年か）だった。
> 入力では当月と前年の値が離れた位置に書かれ、比べるのはモデル任せになっている。
>
> **再現**（デモの合成データ、staged/v1.1.0）
> - 土日祝の日数: 2026-06 は上旬 2日（前年 3日）。旬の行は「上旬 (06/01〜06/10、10日・土日祝 2日) … 前年 2760（土日祝 3日）」。
>   gemma-4-12b と llm-jp-4.1-33b が、2周とも多い・少ないを逆に読んだ（4件中4件）。gemma-4-31b と qwen の2つは6件とも正しく読んだ
> - 天候の群: 「猛暑日 当月 2日 / 2025年08月 11日 平均 +8%」の +8% や、2026-06 の強風の「前年 平均 -5%」を、当月の値として書いた（gemma-4-12b と llm-jp-4.1-33b で3件ずつ、計6件）
> - 天候の日数: 「2日以内はほぼ同じ」は段2だけの規則で、まとめの段では「多かった」「少なかった」と書く
>
> **案**
> - 旬の行に「土日祝 2日（前年 3日、1日少ない）」のように差と向きを付ける
> - 天候の群の差に年を付ける（「前年 11日・平均 +8%（当月は該当が少なく差なし）」）
> - 月の要約の日数に、コードが「前年より多い／ほぼ同じ／少ない」を付ける（2日以内はほぼ同じ）
> - プロンプトの版を上げる

### 7.5 営業レビューのまとめの見出しを、決まった文言に揃える

> **概要**
> まとめの段の指示は「- 予測と実績・前年比較 … 冒頭に…」の形で見出しを示す。モデルによっては「…」まで見出しとして写す
> （「### 予測と実績・前年比較 …」）。`##` で書くモデルもある。表の差し込みは部分一致で見出しを探すので動くが、読み手に見える見出しが崩れる。
>
> **再現**: qwen3.8-flash-next の 2026-04（9件中1件。5つの見出しすべて）。llm-jp-4.1-33b が `##` で書いた（2件）。
>
> **案**
> - 後処理で、見出しの文言で始まり後ろに飾りが付いただけの見出し行を `### <見出し>` に置き換える
>   （保存済みの45件で試し、上の3件だけが直り、ほかの行は変わらないことを確かめた）
> - 指示の書き方を「- 「予測と実績・前年比較」: 冒頭に…」にする

### 7.6 営業レビューのまとめで、数値表の書き換えと見出しの欠けを後処理で確かめる

> **概要**
> まとめの段は「数値表は一字も変えずに置いてください」「次の5つの見出しで構成してください」と指示しているが、出力を確かめているのは
> 数値表の見出しの行があるか（無ければ差し込む）だけ。表の中身の書き換えと、見出しの欠けは、そのまま保存される。
>
> **再現**（qwen3.8-flash-next IQ3_S、thinking OFF、staged/v1.1.0）
> - 2026-05: 数値表の「昼 3243 | 3178 | +2.0%」「夜 … +2.0%」が「2.0%」になった（符号が落ちた）
> - 2026-09: 「運営上の出来事」の後で出力が終わり、「総括」が無い。finish_reason は stop なので打ち切りとして扱われない
>
> **案**
> - 数値表はコードが持っているので、出力の中の数値表の塊を、コードの表で置き直す（`sub_ensure_table` の延長）
> - 5つの見出しがそろっているかを確かめ、欠けていればまとめの段を1回やり直す（思考なしでのやり直しと同じ形）。それでも欠ければ警告を残す

  thinking ON の IQ3_S の「数値をほとんど引かない・入力の書き方に触れる」も、思考の中で指示を守ろうとした結果と読める
- **速さを優先するなら、thinking OFF は有力。** 営業レビュー1件が 20〜30秒で、数値の根拠も保てている
- 引き換えに、まとめの段で推測を足しやすく、数値表の書き換え・見出しの欠けのような**形の崩れ**も出る。thinking OFF で使うなら、
  後処理での検査（改良案 I）と、比較の向きをコードが付ける改良（E）が特に効くはず

## 9. ファイル

| 場所 | 内容 |
|---|---|
| `data/runs.csv` | 1件1行の一覧（条件・所要時間・まとめの段の入力／出力のトークン数と生成の速さ）。出力のトークン数は思考を含む |
| `data/runs/<run_id>.json` | 1件ずつの記録。条件（モデル・推論サーバ・thinking・サンプリング）、本文、段ごとの出力（`review:attendance` など）、実行情報 |
| `data/prompts/<engine>_<月>.md` | 月ごとのプロンプトの全文（多段は段ごと。まとめの段の `<<attendance>>` などには段1〜3の出力が入る） |
| `data/side_by_side/<engine>_<月>.md` | 同じ月の本文をモデルごとに並べたもの |
| `data/export.json` | 生成結果と入力をまとめた JSON（スクリプトが読む） |
| `data/times.tsv` | 1件ごとの所要時間（読み込みを含まない）。`phase` は投入のまとまり（`strataxl*` / `strataiq*` が §8 の thinking OFF） |
| `results/checks.csv` / `findings.jsonl` | 自動の検査（1件1行の集計と、引っかかった行） |
| `results/summary_*.csv` | 所要時間と検査の、モデル別の集計 |
| `results/reading_notes.md` | 目視の記録 |
| `scripts/` | `check_reports.py`（検査）、`summarize.py`（集計）、`render_side_by_side.py`（並べた本文）、`try_heading_normalize.py`（§5.2 の試し）。Python 3 の標準ライブラリだけで動く |
| `conditions/` | 計測で使った llama.cpp の設定（モデル別のプリセットとサンプリング、compose）。`.env` の値は §2.3 |
