# AI レポートのモデル比較（2026-11）

[gfdash](https://github.com/air-terminal/gfdash) の AI レポートを、同じ入力（公開デモの合成データ）でモデルだけを変えて作り、
品質・処理速度・改良の余地を調べた記録です。データは合成なので、来場者数などの数値は実在の施設のものではありません。

- 実施: 2026-11-21〜22
- 1件ずつの記録: [`data/runs/`](data/runs/)（条件・本文・段ごとの出力）、一覧は [`data/runs.csv`](data/runs.csv)
- 月ごとにモデルを並べた本文: [`data/side_by_side/`](data/side_by_side/)、プロンプトの全文: [`data/prompts/`](data/prompts/)
- 目視の記録（誤りの一覧）: [`results/reading_notes.md`](results/reading_notes.md)
- 自動の検査・集計: [`results/`](results/)、スクリプト: [`scripts/`](scripts/)（`data/` だけで動きます）

## 0. 対象の AI レポート

gfdash はゴルフ練習場向けのダッシュボード（Django + PostgreSQL）です。来場者数・天候・運営者の所見（「キャンペーンを行った」などのメモ）から、
ローカルの LLM が月次のレポートを書きます。今回比べたのは次の2種類です。

| 種類 | 中身 | 作り方 |
|---|---|---|
| 見通し（forecast_1m） | 翌月の来場者数の予測（Prophet）を、前年や直近3か月と比べて読む | 1回の生成。思考なし |
| 営業レビュー（review） | 終わった月の来場を、予測・前年・天候・所見と比べて振り返る | **多段（staged）**: 段1 来場の推移 → 段2 天候 → 段3 所見の整理 → 段4 まとめ。段1〜3は思考なし、まとめの段だけ思考あり。数値表と見出しの下の表はコードが作る |
|  |  | **1回（single）**: 月の合計だけを渡して1回で書く軽量版 |

多段にしているのは、月の合計だけを渡すと、月の中で何が起きたかを想像で埋めるためです。各段には「提供されていない数値を作らない」
「天候を来場の増減の理由に断定しない」「業務改善の提案をしない」などの指示があります（プロンプトの全文は [`data/prompts/`](data/prompts/)）。

## 1. 要約

- **数値の書き写しは、どのモデルもほぼ正確。** 営業レビュー（staged）は、本文の数値がすべて入力か段の出力にあった
  （llm-jp だけ、旬の合計と1日平均を並べるなどの混同がある）。崩れた表、思考のタグの残り、他言語の混入は 0 件
- **誤りの中心は「数値の意味」。** 当月の値と前年の値の取り違え、多い／少ないの判定の誤り、予測比と前年比の取り違え。
  数値そのものは正しいので、数値の照合では見つからない
- **プロンプトと前後の処理で防げる誤りが多い。** 特に次の4つは、モデルを替えても起き、入力の書き方が誘っている:
  1. 見通しで、予測値に反映済みの予測所見（+10% / +8%）を、もう一度掛ける（2モデル）
  2. 見通しだけ提案を条件付きで許しているため、許さない月にも提案が出る（3モデル）
  3. 所見の整理の段が、日付の無い出来事に日付を作る（llama.cpp の4モデルすべて、8件中8件）
  4. 前年にだけ差が付いた天候の群（猛暑日 +8% など）を、当月の値として書く（2モデル・6件）
- **モデルごとの傾向**（営業レビュー）:
  - gemma-4-31b … 最も速く（中央値 121秒）、土日祝の日数の読みも正しいことが多い。天候を理由に断定しがち
  - gemma-4-12b … 当月と前年の取り違え・比較の向きの誤りが多い
  - qwen3.8-27b … 因果を断定しない・引用数の上限を守るなど指示に忠実。ただし数値が少なく抽象的で、天候の向きを全部逆にした回がある
  - llm-jp-4.1-33b … 誤りが最も多い。数値を多く並べ（上限3を超える）、取り違え・向きの誤り・因果の断定が6件中5件ずつ。
    「仕事帰りの利用が主因」「売上面では前年を下回った」のような入力に無いことも書く。
    ただしこのモデルだけ、思考を止められず、コンテキスト長と KV キャッシュの設定もほかと違う（§2.3）
  - qwen3.8-flash-next（Strata、IQ3_S）… 指示に最も忠実（所見に日付を作らなかったのはこのモデルだけ）。数値が少なく、
    「差の数値が付いていない」のような入力の書き方への言及が多い。見出しの「…」の写しが 9件中1件で再現した
- **追加の測定（§8）:** qwen3.8-flash-next を thinking OFF で回すと、営業レビューが 347秒 → 23秒（IQ3_S）/ 30秒（Q4_K_XL）になった（中央値）。
  所要時間のほとんどは、まとめの段の思考だった。thinking OFF では数値を具体的に引いて読みやすくなる一方、推測や因果の言い切りが増え、
  数値表の書き換え・見出しの欠けも1件ずつ出た（thinking ON では0件）
- **追加の3モデル（§9）:** gpt-oss-20b は思考を使うモデルで最速（営業レビュー 85秒）だが誤りが多め。gemma-4 26B-A4B は
  **まとめの本文を9件中3件英語で書いた**（思考が英語）。qwen3.6-27b は1世代前でも営業レビューは qwen3.8-27b と同じくらい堅実
- **所見の解析（§10）:** 日付は全モデルが全件正しい。外れたのは種類（予測に効かせる出来事を「記録のみ」にする）で、
  思考を止められない llm-jp（7件）と gpt-oss-20b（8件）に集中した

| モデル | 推論サーバ | 量子化 | コンテキスト | KV キャッシュ | GPU の分割 |

- llama.cpp は同時処理 1（`N_PARALLEL=1`）、Flash Attention あり、`--jinja`
- **llm-jp だけ条件が違う。** KV キャッシュ q8_0 + tensor 分割では生成が 0.86 トークン/秒まで落ちた（入力の処理は正常）。
  f16 + 65,536 は読み込みで GPU のメモリが足りない。f16 + 32,768 にして 約32 トークン/秒に戻った。営業レビューに要るのは 16k なので足りる
- 思考: 営業レビューは `--think`（多段では段1〜3は思考なし、まとめの段だけ思考あり）。見通しは思考なし。
  **llm-jp と gpt-oss-20b は思考を止められない**（OFF を送っても思考する。gpt-oss の強さは既定のまま）

主な例（入力は合成データ）:

- **当月と前年の取り違え**（2026-08）: 入力は「猛暑日 当月 2日 / 2025年08月 11日 平均 +8%」。+8% は前年の値なのに、
  gemma-4-12b（2回とも）と llm-jp が「猛暑日の来場は平均 +8% 多かった」と書いた
- **比較の向き**（2026-06）: 土日祝の日数は上旬 2日（前年 3日）・中旬 3日（2日）・下旬 3日（4日）。gemma-4-12b と llm-jp は
  「下旬は土日祝が前年より多いのに減った」と逆に読んだ。gemma-4-31b・qwen の2つは正しく読んだ
- **比較の向き**（2026-08、qwen3.8-27b の2周目）: 「前年同月比では雨・強い雨・猛暑日は少なく、強風は多かった」→ 4群すべて逆
  （雨 8日 / 3日、強い雨 4 / 2、猛暑日 2 / 11、強風 0 / 5）
- **指標の取り違え**（2026-04）: gemma-4-31b「04/29には前年比+33%」→ +33% は予測比。llm-jp「上旬は1日平均204人で予測2296人を11%下回り」
  → 1日平均と旬の合計を並べた
- **天候を理由に断定**: 「雨や風の発生頻度が高かったことが来場者の減少に寄与」（gemma-4-12b）、「強風が来場抑制に寄与した」（llm-jp）。
  まとめの段の指示「天候を来場者数の増減の理由に断定しない」に反する
- **所見の誤読**（2026-04）: 所見は「料金改定と競合施設の開業の影響が残り前年は下回っている」。gemma-4-12b の1周目は
  「影響は減少しています」と逆に書いた（single も同じ箇所で「前年は…影響を受け」と誤読）

日本語の誤り: 「少く」（qwen3.8-27b）、「ほぼ的に」「【分析総幹】」（gemma-4-31b）。
gemma-4-12b の段3の出力に、異物のトークン（「様子を見るhéと見ている」「様子を見るmigrationsと見ている」）が2回あった。
最終のレポートには残っていない。

### 4.5 2周目（同じ条件でもう一度）

同じモデル・同じ入力でも、誤りの場所は回ごとに変わった（例: gemma-4-12b の 2026-04 は、1周目は所見の誤読、2周目は土日祝の日数の誤り）。
「このモデルはこの誤りをする」より「このモデルはこの型の誤りをしやすい」と読むのが妥当。
見出しの「…」の写しも、Strata の 9件中1件（2周目の 04）だけだった。

### 5.2 後処理で確かめたもの（推論なし）

**見出しの正規化（G）**: まとめの段の出力で、見出しの文言で始まり後ろに飾り（「…」・空白・記号）が付いただけの行を、`### 見出し` に置き換える。
保存済みの staged 90件（§8・§9 を含む）に当てた（`try_heading_normalize.py`）:

- 変わったのは 15件。Strata の「### 予測と実績・前年比較 …」（1件・5見出し）と、llm-jp の `##`（2件）が直った。残りの12件は行末の空白だけ
- 見出しと関係の無い行は変わらない。`sub_insert_section_tables` は今も部分一致で見出しを探しているので、表の差し込みは今も動いている。
  正規化は、読み手に見える見出しを揃えるためのもの

### 5.3 推論で確かめる必要があるもの

A〜E と H はプロンプトや入力の書き方を変えるので、再生成しないと効果が分からない。おすすめの順:

1. **A と B（見通し）**: 1件 15〜50秒と軽く、二重計上は数値として外に出る誤り。07・09・10 × 5モデル = 15件で、約10分
2. **C（段3）**: 段3だけを回せば短い。所見のある 04・07・08
3. **D と E（入力の書き方）**: 全段に効く。06・08 を中心に、2周目まで回してばらつきと分けて見る

## 6. 限界

- 1条件あたり1〜2回の生成で、seed も固定していない。モデルの差と生成ごとのばらつきは、2周目の3か月を除いて分けられない
- 目視は営業レビュー staged の 3か月（30件）が中心。05・07・09 は自動の検査だけ
- サンプリングはモデルごとにカードの推奨値で、揃えていない。qwen3.8 は llama.cpp（思考なしの段も思考ありの値）と Strata（モードで切り替え）で扱いが違う
- llm-jp はコンテキスト長と KV キャッシュがほかと違う（2.3）
- 推論サーバ・量子化・GPU の分割が揃っていないので、速度は「この構成でこの速さ」の比較
- 合成データ 1施設分。実データの月の動きは、もっと荒い可能性がある

### 7.1 見通しで、予測値に反映済みの所見の見立てをもう一度掛けることがある（[gfdash#35](https://github.com/air-terminal/gfdash/issues/35)）

> **概要**
> 見通し（forecast_1m）のプロンプトは、予測所見のイベントを「来場者数への影響の見立て: +8%」の形で渡し、
> 「数値の背景として分析に反映してください」と指示している。一方、予測値（Prophet）はこのイベントを補正としてすでに反映している。
> プロンプトがそれを伝えていないため、モデルによっては予測値にもう一度掛ける。
>
> **再現**（デモの合成データ、Ver2.11.0、forecast/v0.2.0）
> - 2026-07（夏休みキャンペーン +10%）: llm-jp-4.1-33b と qwen3.8-flash-next が「7,102人 × 1.10 ≒ 7,812人」と書いた。キャンペーンは 7/18〜だが月全体に掛けている
> - 2026-10（20周年キャンペーン +8%）: llm-jp-4.1-33b が「7,885 × 1.08 ≈ 8,536人」と書いた
> - 逆に gemma-4-12b は 2026-07 で「7,102人は…+10%を考慮する前のベースラインです」と書いた
> - qwen3.8-flash-next（Q4_K_XL、thinking OFF）は 2026-07 で「メイン予測値 7,102人は、このキャンペーン効果を完全に織り込んだ数値かどうかが明記されていません」と書いた（モデル自身が曖昧さを指摘している）
>
> **案**
> - `com_build_remark_section` の見通し用の行で、予測に使ったイベント（`use_for_forecast` で係数あり）には「（予測値に反映済み）」を添える
> - 見通しのプロンプトに「所見の見立て（%）を予測値に掛け直さないでください。予測値はこの見立てを反映した値です」を足す
> - プロンプトの版を上げる（forecast/v0.3.0）
>
> **確かめ方**: 07・10 を複数のモデルで作り直し、掛け直しが無いことと、反映済みと読めることを見る

### 7.2 見通しのプロンプトだけ、提案を条件付きで許している（[gfdash#36](https://github.com/air-terminal/gfdash/issues/36)）

> **概要**
> 営業レビューは共通の前置き（`COMMON_RULES`）で、業務改善の提案を一切禁じている。`report_common.py` のコメントは、
> 以前の「悪化しているときだけ簡潔に」という条件付きの許可が「想像の入口になっていた」としている。
> 見通し（`report_forecast`）は共通の前置きを使わず、今も「予測値が前年実績を下回るなど…の場合のみ簡潔に」提案を許している。
>
> **再現**（デモの合成データ、Ver2.11.0）: 予測が前年を上回る月（条件では提案しない月）にも提案が出た。
> - 2026-10: qwen3.8-27b が「提案は不要と判断します」と書いた直後に「人員配置や準備を事前に行っておくことを推奨します」
> - 2026-10: qwen3.8-flash-next が見出し「結論と簡潔な提案」を自分で足し、「告知の前倒し実施など…検討してください」
> - 2026-09: llm-jp-4.1-33b が「扇風機設置、ドリンク販売強化を検討すべき」（入力に無い「予約キャンセル」も持ち込んだ）
>
> **案**
> - 見通しも `com_build_common_header` を使い、提案の禁止を営業レビューと揃える

> - プロンプトの版を上げる

### 7.3 営業レビューの所見の整理（段3）が、日付の無い出来事に日付を付ける（[gfdash#37](https://github.com/air-terminal/gfdash/issues/37)）

> **概要**
> 段3の指示は「出来事の名前、日付（期間）、来場者数への影響の向きを必ず残してください」。所見に時期の書かれていない出来事
> （例:「料金改定と競合施設の開業の影響が残り」）にも、モデルは所見の見出し「[2026年04月の所見]」の年月を付ける。
> まとめの段で「料金改定と競合施設の開業は当月に実施され」のような、所見に無い事実になる。
>
> **再現**（2026-04、staged/v1.1.0）: llama.cpp で動かした4モデル（gemma-4-12b / 31b、qwen3.8-27b、llm-jp-4.1-33b）の段3の出力8件すべて（2回ずつ）が、
> 料金改定・競合開業に「2026年04月」を付けた。qwen3.8-flash-next は IQ3_S では2件とも付けなかったが、同じモデルの Q4_K_XL では付けた。
>
> **案**
> - 段3の指示を「日付（期間）は所見に書かれていれば残してください。書かれていなければ『時期の記載なし』と書き、所見の見出しの年月を出来事の日付にしないでください」にする
> - プロンプトの版を上げる（staged/v1.2.0）

### 7.4 営業レビューの入力で、比較の向きをコードが先に付ける（[gfdash#38](https://github.com/air-terminal/gfdash/issues/38)）

> **概要**
> 営業レビューの誤りの多くは、数値の書き写しではなく比較の判定（多い／少ない、当月か前年か）だった。
> 入力では当月と前年の値が離れた位置に書かれ、比べるのはモデル任せになっている。
>
> **再現**（デモの合成データ、staged/v1.1.0）
> - 土日祝の日数: 2026-06 は上旬 2日（前年 3日）。旬の行は「上旬 (06/01〜06/10、10日・土日祝 2日) … 前年 2760（土日祝 3日）」。
>   gemma-4-12b と llm-jp-4.1-33b が、2周とも多い・少ないを逆に読んだ（4件中4件）。gemma-4-31b と qwen の2つは6件とも正しく読んだ
> - 天候の群: 「猛暑日 当月 2日 / 2025年08月 11日 平均 +8%」の +8% や、2026-06 の強風の「前年 平均 -5%」を、当月の値として書いた（gemma-4-12b と llm-jp-4.1-33b で3件ずつ、計6件）
> - 天候の日数: 「2日以内はほぼ同じ」は段2だけの規則で、まとめの段では「多かった」「少なかった」と書く
>
> **案**
> - 旬の行に「土日祝 2日（前年 3日、1日少ない）」のように差と向きを付ける
> - 天候の群の差に年を付ける（「前年 11日・平均 +8%（当月は該当が少なく差なし）」）
> - 月の要約の日数に、コードが「前年より多い／ほぼ同じ／少ない」を付ける（2日以内はほぼ同じ）
> - プロンプトの版を上げる

### 7.5 営業レビューのまとめの見出しを、決まった文言に揃える（[gfdash#39](https://github.com/air-terminal/gfdash/issues/39)）

> **概要**

### 7.6 営業レビューのまとめで、数値表の書き換えと見出しの欠けを後処理で確かめる（[gfdash#40](https://github.com/air-terminal/gfdash/issues/40)）

> **概要**
> まとめの段は「数値表は一字も変えずに置いてください」「次の5つの見出しで構成してください」と指示しているが、出力を確かめているのは
> 数値表の見出しの行があるか（無ければ差し込む）だけ。表の中身の書き換えと、見出しの欠けは、そのまま保存される。

> **再現**（qwen3.8-flash-next IQ3_S、thinking OFF、staged/v1.1.0）

> - 2026-09: 「運営上の出来事」の後で出力が終わり、「総括」が無い。finish_reason は stop なので打ち切りとして扱われない

### 7.8 所見の解析: 休業・営業時間の変更を、計画休業の印と係数のどちらで表すかが決まっていない（解析の失敗・二重掛け・効き不足）（[gfdash#42](https://github.com/air-terminal/gfdash/issues/42)）

> **概要**
> 休業や営業時間の変更は、予測に2つの経路で入り得る。
>
> - **計画休業の印**（日々の記録の `temp_closed`）: 朝（8〜12時）・昼（12〜17時）・夜（17〜23時）の時間帯ごとに付け、印の付いた時間帯を丸ごと休業として、
>   過去の計画休業の実績から求めた割合（休業中の客が営業中の時間帯へ流れる割合など）で補正する（`com_get_closure_factor`）。上下限で切らない
> - **所見の係数**（所見の解析で確定したイベント）: 運営者の見立てを掛ける。1日の合成係数は 0.5〜1.5 で切られる（`EVENT_FACTOR_MIN` / `EVENT_FACTOR_MAX`）
>
> どちらを使うかの決まりが無いため、次のことが起きる。
>
> - 終日休業を所見に書くと、モデルが「来場0」と読んで係数 0.0 を出し、係数の範囲（0.1〜3.0）外で**解析そのものが失敗する**。下限の 0.1 を置くモデルもあるが、予測では 0.5 で切られる
> - 時間帯の区切りに合う変更（終日休業、「17時より営業開始」= 朝＋昼の休業）は印で正確に表せるのに、係数でも入れると**二重に効く**
> - 時間帯の途中で変わる日（「15時より営業開始」など）は、印では表せない。朝＋昼に印を付けると15〜17時の営業分が無いことになり少なく、朝だけだと昼の休業分が抜けて多く見積もる。
>   この日は係数（運営者の見立て）が必要だが、**0.5 より下の見立ては切られて効き不足になる**
>
> **再現**（`parse/v0.2.0`、対象月 2026-08、9構成）:
> - 「8/1にメンテナンスの為休業する」: gemma-4 12B・31B、qwen3.6-27b が係数 0.0（範囲外で解析が失敗）。qwen3.8-27b・gpt-oss-20b は 0.1。残りの4構成は係数なし
> - 「8/5(水)設備点検のため営業時間変更(17時より営業開始。当日は来場者数50%まで減少すると予想)」: 8構成が係数 0.5（区切りに合う変更なので、印でも表せる）
>
> **案**: 変更の形で使い分け、同じ日に印と係数を重ねない
>
> | 変更の形 | 例 | 使うもの |
> |---|---|---|
> | 終日休業 | 8/1に休業 | 休業の印（終日）。係数は使わない |
> | 時間帯の区切りに合う | 17時より営業開始、17時で閉店 | 休業の印（朝＋昼／夜）。係数は使わない |
> | 時間帯の途中で変わる | 15時より営業開始、14時で閉店 | 係数（運営者の見立て）。印は付けない（付けるなら係数とどちらか一方） |
>
> - 解析のプロンプト: 終日休業には係数を出さない（0.0 を出さない）。区切りに合う変更は記録のみにする。時間帯の途中の変更は、本文に数量があれば係数にしてよい
> - 確定の画面: 終日休業・区切りに合う変更には「日々の記録に計画休業の印を付けてください」と案内する。同じ日に係数と計画休業の印が両方あれば「二重に効きます。どちらか一方にしてください」と警告する
> - 時間帯の途中の変更の係数が 0.5 より下なら、確定の画面で「予測では 0.5 で切られます」と知らせる。営業時間の変更による係数を上下限の対象から外すか（休業の印と同じく確定情報として扱う）は要検討
> - 予測の実行: 同じ日に印と係数が重なったら実行の記録（note）に残す
> - プロンプトの版を上げる

### 7.9 所見の解析: 「8/1に休業」のような1日だけの出来事を「1日だけとは書かれていない」と誤って指摘する（[gfdash#43](https://github.com/air-terminal/gfdash/issues/43)）

> **概要**
> 本文の検査（`com_check_grounding`）は、開始日と終了日が同じイベントに、本文に「当日・のみ・だけ・1日・限り」が無ければ
> 「開始日を複写した可能性があります」と出す。「8/1に休業する」「8/22(土)試打会」のように、日付が1つで終わりを示す語も始まりを示す語（から・より・以降）も無い書き方は、
> 普通は1日だけの出来事なのに指摘される
>
> **再現**: 「8/1にメンテナンスの為休業する」を qwen3.8-27b が 8/1〜8/1 と読み（正しい）、この指摘が出た
>
> **案**
> - 日付の表現が1つで、始まりを示す語（から・より・以降・以後）も終わりを示す語も無いときは、1日だけの出来事とみなして指摘しない
> - 複数の項目を書いた所見（見出しや「・」で分けたもの）は、本文全体ではなく項目ごとに判定する（日付が2つ以上あっても、項目ごとには1つのことが多い）
> - 判定の例を `com_remark_samples` かテストに足す

### 7.10 所見の解析: 天候の見込みは係数ではなく、予測の気温の前提に反映する（[gfdash#44](https://github.com/air-terminal/gfdash/issues/44)）

> **概要**
> 「猛暑日が多くなる予報。昼の来場は2割ほど減りそう」のように数量つきで天候の見込みを書くと、ほぼすべてのモデルが係数（0.8 前後）を置く。
> 根拠の検査が「天候は予測モデルが気温の回帰変数で扱っています。予測の補正には使わないことを勧めます」と指摘するが、確定は止めない。
> 予測モデルは気温を回帰変数に持つので、係数で掛けると気温の効果を二重に数えるおそれがある。一方、見通しの気温の前提は平年値（±2℃のシミュレーション）で、
> 「平年より暑い」という見込みを予測に入れる手段が無い。運営者が書きたいのはこの見込み
>
> **再現**（`parse/v0.2.0`、9構成）:
> - 「猛暑日が多くなる予報。昼の来場は2割ほど減りそう」: 8構成が 0.80 前後（1日全体の2割減として扱う）。Flash-Next Q4_K_XL だけが「昼に限った影響」として全体 0.95 に読み替えた
> - llm-jp は名前を「暑天による…」にし、天候の指摘が出なかった（`WEATHER_MARKERS` に「暑天」が無い）
> - 「今夏は猛暑日が多くなる長期予報が出ている」（数量なし）: 9構成とも係数を置かない（正しい）
>
> **案**
> - 天候の見込みは係数にせず、見通しの気温の前提（平年値）をずらす入力として扱う（例: 「平年より高い」→ メインの予測を +1℃ や +2℃ の前提で出す）。どこで受けるか（所見の解析の新しい種類か、見通しの画面の設定か）は要検討
> - それまでの間は、解析のプロンプトに「天候の見込みは係数にしない（記録のみ）」を足し、天候の指摘を警告から確定前の確認に強める
> - `WEATHER_MARKERS` に「暑天・高温・暑い」などを足す
> - 時間帯（昼だけ・夜だけ）の影響は係数で表せない。プロンプトで「時間帯の限定がある場合は記録のみ」とするか、時間帯つきの係数を持つかを決める

### 7.11 所見の解析: 数量の書かれていない所見に、画面で数量を聞き返す（[gfdash#45](https://github.com/air-terminal/gfdash/issues/45)）

> **概要**
> 運営者が書き慣れていないと、所見は「キャンペーンをやる」「近くに練習場ができる」のように数量の無い文になりやすい。
> 数量が無いと、モデルによって「係数なし（記録のみ）」と「推測の係数」に分かれる（§10: qwen3.6-27b は9件すべてに係数を置いた。追加の4件でも、数量の無い猛暑の行に 0.95 を置いた）。
> どちらになっても、運営者は「予測に効かせるならどれくらいか」を考える機会が無いまま確定しがち
>
> **再現**: §10 のデモの所見9件（数量なし）と、§10.1 の heat_vague・structured の猛暑の行
>
> **案**
> - 解析の結果に係数の無いイベント（または根拠の検査で「数量が所見に見当たりません」が出たイベント）があれば、画面で「予測に効かせますか？　効かせるなら、どれくらい増減しそうですか（例: 1割増）」と聞き返す欄を出す
> - 運営者の答えは根拠（rationale）に残し、係数はそこから決める（推測の係数を AI に置かせない）
> - 書き方の例（期間・数量の書き方）を所見の入力欄の近くに出す

### 10.1 追加の4件: 書き方を変えると（2026-11-24）

note ♯2 で例に挙げる書き方（休業・天候の見込み）を、上の14件では試していなかったので足した。条件は §10 と同じ（`parse/v0.2.0`、思考 OFF、9構成）。
正解は決めず、各モデルの出力をそのまま比べる。対象月は 2026-08。

| キー | 所見 | 見たいこと |
|---|---|---|
| heat_vague | 今夏は猛暑日が多くなる長期予報が出ている | 日付も数量も無い天候の見込み |

**heat_vague**: 9構成とも係数を置かず、予測に使わない。種類は「記録のみ」6構成、「期間限定（係数なし）」3構成（gemma-4 26B-A4B・qwen3.8-27b・Flash-Next IQ3_S）。
Flash-Next Q4_K_XL は「減るのか、屋内需要で増えるのかも分からない」と向きまで保留した

**closed_1day**（差が最も大きい）:

| 扱い | 構成 |
|---|---|
| 係数 0.0 を出し、範囲（0.1〜3.0）外で**解析が失敗** | gemma-4 12B・31B、qwen3.6-27b |
| 下限の 0.1 を置いた | qwen3.8-27b（8/1〜8/1）、gpt-oss-20b（終了日なし） |
| 係数を置かず、予測に使わない | gemma-4 26B-A4B、llm-jp（記録のみ）、Flash-Next IQ3_S・Q4_K_XL（期間限定・終了日なし） |

- 「休業 = 来場0」は自然な読みだが、係数では表せない。予測には計画休業の補正（`com_forecast.py`。日々の記録の休業の印から、実績で割合を求める）が別にあり、
  終日休業や時間帯の区切りに合う変更は本来そちらにつなぐ出来事。時間帯の途中で変わる日は印で表せないので係数が要る（7.8）
- qwen3.8-27b の「8/1〜8/1」に、本文の検査が「1日だけの出来事とは書かれていません」と出した（誤検知。`SAME_DAY_MARKERS` に「8/1に」の形が無い）
- 終了日の無い「期間限定」は、確定のときに `com_check_events` が止める（「終了日を入力してください」）。黙って以後ずっと効くことは無い

**heat_rate**: 8構成が中央 0.80 前後を置いた（「昼の2割減」を1日全体の2割減として扱う）。**Flash-Next Q4_K_XL だけ**「昼に限った影響なので全体では 0.95（0.90〜1.00）」と読み替えた。
根拠の検査の天候の指摘（「天候は予測モデルが気温の回帰変数で扱っています…」）は8構成で出た。llm-jp は名前を「暑天による…」にしたため出なかった（`WEATHER_MARKERS` に「暑天」が無い）

**structured**:

- 3つの予定（0.5 / 1.01 / 0.95、日付）は gpt-oss-20b 以外の8構成が正しく読んだ
- 猛暑の行は、8構成が係数を置かなかった。**qwen3.6-27b だけ**書かれていない 0.95 を置いた（§10 の「9件すべてに係数」と同じ傾向）
- **gpt-oss-20b**: イベント名が英語（"August Heatwave Impact" など）、書かれていない店名 "Oasis" を作った、8/5 と 8/22 の終了日を空けた（確定のときに止まる）
- Flash-Next Q4_K_XL は値は正しいが、幅を自分で広げた（0.4〜0.6、1.00〜1.05）
- 8/5 の「17時より営業開始」は時間帯の区切り（朝＋昼の休業）に合うので休業の印で表せる。係数 0.5 と印の両方を入れると二重に効く

読み方: 数量・日付がはっきり書かれていれば、モデルを問わずほぼ正確に読む。書かれていないとき（休業・天候・時間帯）の振る舞いはモデルで大きく違い、
一部は仕組みの側で表せない（係数0、昼だけの影響）。→ 7.8〜7.11（gfdash#42〜#45）
